## 1. Hard blockers — Neovim misbehaves at startup

### 1.1 `vim.o.shell = '/bin/sh'` — `lua/config/options.lua:3`

There is no `/bin/sh` on native Windows. Every shell-mediated operation breaks:
`:!`, `:terminal`, `vim.fn.system()` with a string argument, `system()`-based
plugin fallbacks, and any lazy.nvim `build` string (which is run through `'shell'`).

This is the single change most likely to make the difference between "config
loads" and "config loads and works".

Options, in rough order of preference:

- `pwsh` (PowerShell 7) — cross-platform, and you would be installing it anyway
  since Mason requires `pwsh` or `powershell` on Windows.
- `powershell` — the in-box Windows PowerShell 5.1; works, but older.
- `cmd.exe` — simplest, least capable.

Note that switching `'shell'` to PowerShell also requires `shellcmdflag`,
`shellquote`, `shellxquote`, `shellpipe`, and `shellredir` to be set
consistently, or `:!` and `system()` quoting will misbehave. Getting this
half-right is a common source of subtle breakage; budget real time for it.

The comment on this line ("POSIX compatible shells are needed by some plugins")
is worth revisiting as part of the port — identify *which* plugins actually need
it, because that determines whether `cmd.exe` is acceptable or whether you need
a genuine POSIX shell on PATH (which would contradict the no-emulation-layer
constraint).

### 1.2 `term fish` keymaps — `lua/config/keymaps.lua:15-16`

```lua
km('n', '<m-f>', '<cmd>vsplit<bar>term fish<cr>i', ...)
km('n', '<m-F>', '<cmd>split<bar>term fish<cr>i', ...)
```

`fish` has no native Windows build. Per your MSYS2 thread, the only fish on
Windows is the `msys` repo build linked against `msys-2.0.dll` — which is the
emulation layer you have ruled out for this machine.

These need a per-platform shell choice (`pwsh` on Windows). Since `:term` with
no argument uses `'shell'`, one option is to fix `'shell'` correctly and change
these to bare `<cmd>vsplit<bar>term<cr>i`, which removes the platform
conditional entirely.

## 2. Path construction bugs

### 2.1 codelldb command path — `lua/plugins/debug.lua:132`

```lua
command = vim.fn.stdpath 'data' .. '/mason/bin/codelldb',
```

Two problems:

1. Hardcoded `/` separator (cosmetic — Neovim accepts forward slashes on
   Windows — but inconsistent with the `vim.fs.joinpath` used everywhere else,
   including the debugpy block 20 lines above).
2. **No file extension.** Mason's `bin` directory on Windows contains `.cmd`
   shims, not extension-less executables. An absolute path to `codelldb` with
   no extension will not resolve.

Since `lua/config/tooling.lua:16-18` already prepends Mason's `bin` to
`vim.env.PATH`, the cleanest fix is to resolve through PATH and let Neovim apply
`$PATHEXT`:

```lua
command = vim.fn.exepath 'codelldb',
```

Worth verifying empirically on the Windows box — check that
`:lua = vim.fn.exepath('codelldb')` returns a `.cmd` path after Mason installs it.

### 2.2 codelldb program prompt — `lua/plugins/debug.lua:145`

```lua
vim.fn.getcwd() .. '/',
```

Cosmetic. Works on Windows, but displays a mixed-separator path in the prompt.
`vim.fs.joinpath` won't produce a trailing separator, so if you want this
cleaned up it needs an explicit conditional or `package.config:sub(1,1)`.

### 2.3 Debugpy path — `lua/plugins/debug.lua:110-112`

Already correct. `venv/Scripts/python.exe` vs `venv/bin/python` is handled, and
this is the model the rest of the config should follow.

### 2.4 Mason PATH separator — `lua/config/tooling.lua:15-18`

Already correct. `vim.fn.has 'win32'` returns 1 on 64-bit Windows (it means
"Windows", not "32-bit"), so the `;` / `:` selection is right.

### 2.5 Node-local LSP binaries — `lsp/cssls.lua:29`, `lsp/html.lua:31`

```lua
vim.fs.joinpath(config.root_dir, 'node_modules/.bin', cmd)
```

On Windows, npm creates `.cmd` shims in `node_modules\.bin`, so the resolved
path has no extension. `vim.fn.executable()` appends `$PATHEXT` when testing, so
the *check* will likely pass — but the extension-less path is then handed to
`vim.lsp.rpc.start()` for spawning. Whether that spawn succeeds needs testing
rather than assumption. If it fails, `vim.fn.exepath()` on the result is the fix.

### 2.6 Neorg workspace — `lua/plugins/neorg.lua:17`

`notes = '~/neorg'`. Neorg expands this itself, and `~` maps to `%USERPROFILE%`
on Windows, so this should work — but it is the one remaining hardcoded home
path and worth confirming.

## 3. Build-time / external toolchain requirements

### 3.1 telescope-fzf-native — `lua/plugins/infrastructure.lua:54-56`

```lua
build = 'make',
cond = function() return vim.fn.executable 'make' == 1 end,
```

<cite index="5-1">fzf-native ships no binaries; it must be built with either cmake or make. The cmake path requires CMake plus the Microsoft C++ Build Tools on Windows.</cite> There is no `make` on native Windows, so the
`cond` will evaluate false and the extension will silently not build — meaning
`telescope.load_extension 'fzf'` at `infrastructure.lua` will then error, since
that call is unconditional in your `config` function.

**This is a latent bug even on Linux:** if `make` is ever absent, `cond` disables
the plugin but `load_extension 'fzf'` still runs. Worth fixing regardless of
platform.

Suggested shape:

```lua
build = vim.fn.executable 'cmake' == 1
      and 'cmake -S. -Bbuild -DCMAKE_BUILD_TYPE=Release'
         .. ' && cmake --build build --config Release'
         .. ' && cmake --install build --prefix build'
   or 'make',
cond = function()
   return vim.fn.executable 'cmake' == 1 or vim.fn.executable 'make' == 1
end,
```

and guard the `load_extension 'fzf'` call with `pcall`.

One caveat worth knowing before you commit to this: there is an open upstream
issue (#157, Nov 2025) reporting that the cmake build places `libfzf.dll` in
`build/Release/` while the loader expects it in `build/`. The `--install ... --prefix build`
step in the command above is what works around this. Verify the DLL lands where
`fzf_lib.lua` looks for it.

### 3.2 nvim-treesitter parser compilation — `lua/plugins/infrastructure.lua:229-253`

You are on `branch = 'main'` with `require('nvim-treesitter').install(...)` over
a large parser list in `lua/config/treesitter.lua`. Every parser is compiled from
C on the local machine. Windows needs one of: MSVC (`cl`), `zig cc`, `gcc`
(MinGW), or `clang`.

Given you already run `zls` and have `after/ftplugin/zig.lua`, installing Zig via
Scoop and letting nvim-treesitter use `zig cc` is probably the least-friction
option — it avoids pulling in the full MSVC Build Tools solely for parsers.

### 3.3 blink.pairs — `lua/plugins/visual_editing.lua:130-135`

`require('blink.pairs').download():wait(60000)` downloads a prebuilt Rust binary
rather than compiling. Windows prebuilts exist, so this should be fine, but the
60-second timeout may be tight on a slow corporate network. Watch for it.

### 3.4 Mason external requirements

<cite index="10-1">Mason on Windows requires `pwsh` or `powershell`, `git`, GNU tar, and one of 7zip / peazip / archiver / winzip / WinRAR.</cite> <cite index="13-1">It also shells out to external package managers such as cargo and npm depending on which packages you install; `:checkhealth mason` lists the full set.</cite>

Your `config/tooling.lua` package list implies, at minimum: **npm/node**
(bash-language-server, css-lsp, cssmodules-language-server,
css-variables-language-server, html-lsp, markuplint, eslint_d), **Python/pip**
(ruff, zuban, debugpy, gitlint), **cargo** (ast-grep, tombi possibly), and
**Go** for some linters. Each of those toolchains has to exist natively on
Windows before `:MasonToolsInstall` will succeed.

Note that Windows 10+ ships `tar.exe` (bsdtar), which Mason generally accepts.

### 3.5 lazy.nvim rocks — `lua/core/lazy.lua:27-30`

`rocks = { enabled = true }` — this is for Neorg's luarocks dependencies.
lazy.nvim's rocks support wants `luarocks`, and its hererocks fallback needs
Python plus a C toolchain. This is historically the roughest part of running a
Neorg-enabled config on Windows.

Flagging this as **verify before assuming**: run `:checkhealth lazy` on the
Windows box early. If rocks won't bootstrap, you may need to either declare
Neorg's Lua dependencies as ordinary plugin specs or drop Neorg on Windows via
`cond`.

## 5. Deployment — `bin/` install scripts

`bin/nvimInstall` is `#!/bin/sh`, and `bin/sourced/configure_xdg_dirs.sh` builds
`$XDG_CONFIG_HOME` etc. from `$HOME` with `chmod 0755` calls. None of this runs
natively on Windows.

Two strategic options:

**(a) Set XDG variables on Windows.** Neovim honors `XDG_CONFIG_HOME` and
`XDG_DATA_HOME` on Windows if they are set, falling back to `%LOCALAPPDATA%\nvim`
and `%LOCALAPPDATA%\nvim-data` otherwise. Setting them as user environment
variables lets your existing directory layout carry over unchanged, and keeps the
config's `stdpath` calls returning familiar shapes.

**(b) Accept Windows defaults** (`%LOCALAPPDATA%\nvim`) and write a PowerShell
port of `nvimInstall` that mirrors the whitelist logic.

(a) is less work and keeps one mental model; (b) is more idiomatic for the
platform. Either way the whitelist install script needs a PowerShell counterpart —
that logic is the part actually worth porting, not the XDG scaffolding.

## 6. Repo hygiene

### 6.1 Line endings

Cloning the dotfiles repo on Windows with the default `core.autocrlf=true` will
convert files to CRLF on checkout. Lua tolerates CRLF, but your POSIX shell
scripts under `bin/` and `spell/en.utf-8.add` will not fare as well, and the
round-trip will show spurious diffs when you push from Windows.

Add a `.gitattributes` at the repo root before the first Windows clone:

```
* text=auto eol=lf
```

This is cheap now and annoying to retrofit after a CRLF commit lands.

### 6.2 `vim.o.fileformats = 'unix,mac,dos'` — `lua/config/options.lua:8`

Existing files keep their detected format; new files get `unix` (LF). On Windows
that means new files are written with LF. That is very likely what you want given
the repo is shared with Linux — noting it here only so it is a decision rather
than an accident.

## 7. Suggested structural change

Rather than scattering `vim.fn.has 'win32' == 1` conditionals (currently in two
places, soon to be six or eight), consider a small `lua/lib/platform.lua`:

```lua
local M = {}

M.is_windows = vim.fn.has 'win32' == 1
M.is_macos = vim.fn.has 'mac' == 1
M.is_linux = not M.is_windows and not M.is_macos

M.path_sep = M.is_windows and '\\' or '/'
M.path_list_sep = M.is_windows and ';' or ':'

---Default interactive shell for `:terminal`.
M.shell = M.is_windows and 'pwsh' or 'fish'

---Resolve an executable, tolerating Windows `.cmd`/`.exe` shims.
---@param name string
---@return string|nil
function M.exe(name)
   local path = vim.fn.exepath(name)
   return path ~= '' and path or nil
end

return M
```

This fits your existing `lua/lib/` convention (`functional`, `mason`, `scroll`,
`text`), keeps the platform tests in one auditable place, and gives the
`config.tooling` PATH block, the DAP specs, and the terminal keymaps a shared
vocabulary.
